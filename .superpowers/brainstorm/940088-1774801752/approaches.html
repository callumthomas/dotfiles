Architecture Approaches

How should we structure the AGS bar codebase? Pick the one that feels right.

A

Widget-per-module — Recommended

Each module (audio, network, bluetooth, etc.) is a self-contained TypeScript file that exports a bar button + its dropdown panel. One shared popup manager controls which panel is open.


Pros

  • Each module is independent — add/remove without touching other code
  • Easy to iterate on one module without breaking others
  • Clear file structure: widgets/audio.tsx, widgets/network.tsx
  • Shared popup manager handles open/close, positioning, click-outside-to-dismiss

Cons

  • Some shared patterns (sliders, toggle rows) need extracting into common components
  • Popup manager adds a bit of coordination complexity

Structure:

ags/
├── app.ts                  # Entry point, window definitions
├── bar/
│   ├── Bar.tsx             # Bar layout (left/center/right)
│   └── PopupManager.ts    # Singleton: tracks open popup, handles dismiss
├── widgets/
│   ├── workspaces.tsx      # Workspace buttons
│   ├── window-title.tsx    # Active window display
│   ├── audio.tsx           # Button + dropdown panel
│   ├── network.tsx         # Button + dropdown panel
│   ├── bluetooth.tsx       # Button + dropdown panel
│   ├── battery.tsx         # Button + TLP dropdown panel
│   ├── system-stats.tsx    # Button + unified CPU/mem/temp panel
│   ├── clock.tsx           # Button + calendar dropdown
│   ├── media.tsx           # Now-playing bar widget + controls
│   ├── notifications.tsx   # Bell + notification center panel
│   └── power.tsx           # Power menu dropdown
├── components/
│   ├── Slider.tsx          # Reusable volume/brightness slider
│   ├── ToggleRow.tsx       # Label + toggle switch row
│   └── DeviceList.tsx      # Reusable device list (BT/audio)
└── styles/
    └── style.css           # GTK4 CSS — replaces your current waybar style
B

Monolithic bar file

Everything in one or two large files — the bar definition, all widgets, all popups. Simpler to start, harder to maintain.


Pros

  • Fastest to get a first version running
  • No import/export ceremony, everything is right there
  • Good for prototyping before committing to a structure

Cons

  • Will become a 1000+ line file quickly with 10 modules + panels
  • Hard to work on one module without scrolling past everything else
  • Refactoring later is more work than starting organized
C

Feature-folder modules

Each module gets its own directory with separate files for the button, panel, services, and styles. Maximum separation.


Pros

  • Maximum isolation — each module is a mini-project
  • Per-module styles, services, and types
  • Scales well if modules grow complex

Cons

  • Lots of directories and boilerplate for simple modules (power menu doesn't need 4 files)
  • Over-engineered for this scope — most modules are ~50-150 lines total
  • More navigation overhead when editing
